# call me maybe

## Description

This project implements **LLM function calling** with **constrained decoding**.

Given a natural-language request such as *"What is the sum of 2 and 3?"*, the program does **not** answer `5`. It asks a small local model (`Qwen/Qwen3-0.6B`) to emit a structured JSON **function call**:

```json
{"name": "fn_add_numbers", "parameters": {"a": 2, "b": 3}}
```

Small models often break JSON when left unconstrained. Here, every generated token is filtered so the output always stays a valid prefix of a schema-compliant call (function name from the catalog, parameter keys in definition order, typed values).

The stack is Python 3.10+, `uv`, `pydantic`, `numpy`, and the provided `llm_sdk` wrapper (no direct use of `transformers` / `torch` / `outlines` in application code).

## Algorithm explanation

Generation is a token-by-token loop on top of `llm_sdk.Small_LLM_Model`:

1. Build a text prompt listing available functions and the user request (`prompt_builder.py`).
2. `encode` the prompt to token ids.
3. At each step call `get_logits_from_input_ids` to get next-token scores.
4. Walk candidate token ids in **descending logit order**.
5. Map each id to the raw **bytes** it stands for via `vocab.json` (`get_path_to_vocab_file`). Qwen uses byte-level BPE: every byte is written as one printable character (`Ġ` = space, `Ċ` = newline, `Ã©` = the two bytes of `é`), so the table is inverted and the generated bytes are decoded as UTF-8. A token that ends in the middle of a multi-byte character is checked with a placeholder character, which is legal only inside strings.
6. Accept the **first** token such that `generated + token` is still a valid **prefix** of some legal call JSON (`constraints.py`). That token is the constrained argmax.
7. Append it and repeat until the checker reports a complete, `json.loads`-able object.
8. Return `{prompt, name, parameters}`.

The prefix checker enforces:

- object shape `{"name": "...", "parameters": {...}}` (optional whitespace);
- `name` must be one of the defined function names (trie / prefix match while the string is open);
- after the name is known, parameter keys must follow the definition order;
- values must match declared types (`number`, `integer`, `string`, `boolean`, `null`, `array`, `object`; any JSON value for an unknown type), including incomplete prefixes (e.g. open strings, partial numbers);
- the checker is **prefix-closed**: it only accepts text that can still be completed into JSON that `json.loads` accepts. Leading zeros (`01`), invalid escapes (`\q`) and raw control characters inside strings are rejected as soon as they appear, so generation never walks into a dead end.

Invalid tokens never win, so the final string is always parseable JSON matching the schema when generation finishes successfully.

### How `_match_call` reads a call

`_match_call` (in `constraints.py`) walks the text left to right with a cursor
and checks it in five parts:

```text
{"name":"fn_add_numbers","parameters":{"a":2.0,"b":3.0}}
└──1──┘└──────2───────┘└──────3──────┘└────────4───────┘└5┘
```

| Part | What it checks |
|---|---|
| 1 | `{` `"name"` `:` with `need` |
| 2 | the function name: a key of `_by_name`, or the start of one while the quote is still open |
| 3 | `,` `"parameters"` `:` `{` with `need` |
| 4 | each parameter of that function in definition order: `,` (not before the first), `"a"`, `:`, then the value with `_match_value_prefix`, which picks the check for its type |
| 5 | the two closing `}` `}` with `need` |

Each part returns the position after it (go on), `-1` when the text ends
inside it (valid so far, stop here) or `None` (invalid). `check` turns the
final answer into `ParseResult`: `None` is `ok=False`, `-1` is `ok=True`, and a
position is `complete=True` once nothing but whitespace follows and
`json.loads` accepts the text.

### Prompt example

`build_prompt` turns the function definitions and one user request into a
single plain text (no chat template). The rules are fixed; the function list
is generated from `functions_definition.json`; only the `User request` line
changes between prompts. The model continues the text after `JSON:`.
This is the exact prompt for `Greet shrek` with the sample definitions:

```text
You are a function-calling system. Choose the ONE function that fulfils the user request and fill in its arguments.
Rules:
- Output only the JSON call, nothing else.
- Take argument values from the request. Copy quoted text exactly, without the surrounding quotes.
- Numbers are plain JSON numbers, not strings.
- When an argument is a regular expression, write a pattern that matches what the user describes, not the words of the description. For a kind of character, use a character class that lists every member of that kind (e.g. [a-zA-Z] for letters). Use + to match a run of characters.
- When the user names a symbol in words, use the symbol itself.

Available functions:
- fn_add_numbers: Add two numbers together and return their sum.
    a (number)
    b (number)
    call: {"name":"fn_add_numbers","parameters":{"a":<number>,"b":<number>}}
- fn_greet: Generate a greeting message for a person by name.
    name (string)
    call: {"name":"fn_greet","parameters":{"name":<string>}}
- fn_reverse_string: Reverse a string and return the reversed result.
    s (string)
    call: {"name":"fn_reverse_string","parameters":{"s":<string>}}
- fn_get_square_root: Calculate the square root of a number.
    a (number)
    call: {"name":"fn_get_square_root","parameters":{"a":<number>}}
- fn_substitute_string_with_regex: Replace all occurrences matching a regex pattern in a string.
    source_string (string)
    regex (string)
    replacement (string)
    call: {"name":"fn_substitute_string_with_regex","parameters":{"source_string":<string>,"regex":<string>,"replacement":<string>}}

User request: Greet shrek
JSON:
```

The model, guided by the mask, completes it with
`{"name": "fn_greet", "parameters": {"name": "shrek"}}`.

### From vocab.json to bytes

The model returns token ids; the checker needs the text of a candidate.
`vocab.json` (from `get_path_to_vocab_file`) maps 151,643 token strings to ids,
written in byte-level BPE notation: each of the 256 possible bytes has its own
visible character (`Ġ` = space `0x20`, `Ċ` = newline `0x0A`, the two bytes of
`é` are `Ã©`). When the decoder is created, `build_id_to_bytes` reverses the
mapping and decodes every token into real bytes:

```python
# bytes_to_unicode(): 256 pairs byte -> character, e.g. {32: 'Ġ', 65: 'A', 208: 'Ð', ...}
byte_decoder = {char: byte for byte, char in bytes_to_unicode().items()}
# {'Ġ': 32, 'A': 65, 'Ð': 208, ...}

for token, token_id in vocab.items():           # ("Ġsum", 2629)
    result[token_id] = token_to_bytes(token, byte_decoder)
                       # 'Ġ'->32, 's'->115, 'u'->117, 'm'->109 -> b' sum'
# result[2629] = b' sum'
# result[963] = b'\xc3\xa9'              ("Ã©", the UTF-8 bytes of "é")
```

The table is built once (`model_post_init`) and only read during generation.
Values are bytes, not strings, because a token can hold half of a multi-byte
character.

### What the decoder holds

`load_decoder(functions)` is called once, before the loop over prompts. It
loads the model and builds a `ConstrainedDecoder`; pydantic then calls
`model_post_init`, which fills the private fields. The same object serves
every prompt:

```text
decoder: ConstrainedDecoder
|
+-- llm            Small_LLM_Model
|                  loaded Qwen3-0.6B (1.4 GB of weights, on mps / cuda / cpu)
|                  encode(text) -> token ids
|                  get_logits_from_input_ids(ids) -> 151,936 scores
|
+-- functions      list[FunctionDefinition], read from functions_definition.json
|                  used by build_prompt (the function list in the prompt)
|
+-- _checker       FunctionCallPrefixChecker
|   +-- functions    the same definitions
|   +-- _by_name     {"fn_add_numbers": <definition>, "fn_greet": <definition>, ...}
|   +-- check(text)  -> invalid / valid prefix / complete
|
+-- _id_to_bytes   dict[int, bytes], 151,643 pairs built from vocab.json
|                  {2629: b' sum', 606: b'name', 4913: b'{"', ...}
|
+-- methods
    +-- generate(prompt)    -> FunctionCallResult   (called by the pipeline)
    +-- _select_token(...)  -> best token the checker accepts
    +-- check_bytes(...)    -> bytes -> text -> _checker.check
    +-- _to_result(...)     -> wraps the parsed call in FunctionCallResult
```

### Inside one `get_logits_from_input_ids` call

The decoder only passes token ids; everything else happens inside the model,
once per generation step (numbers from the Qwen3-0.6B `config.json`):

1. It receives the ids: the prompt (about 393 ids) plus the tokens generated so far.
2. Each id selects one row of the embedding table (151,936 rows x 1,024 numbers),
   so the text becomes a list of vectors. The table lives in the model weights;
   `vocab.json` only maps text to the same ids.
3. The vectors go through 28 transformer layers, where every position attends
   to the previous ones, so the last vector carries the whole context.
4. That last vector is compared (dot product) with the vector of every token in
   the table, giving one score per token.
5. It returns those 151,936 scores as a plain `list[float]`: the logits. The
   index is the token id; they are raw scores, not probabilities.

The decoder then sorts the ids by score, looks up each candidate's bytes in
`_id_to_bytes` and keeps the first one the checker accepts.

### The whole flow, step by step

1. **Load once.** `load_decoder(functions)` loads the model and its tokenizer
   (two separate objects from the same Hugging Face folder) and builds the
   `ConstrainedDecoder` shown above, with `_checker` and `_id_to_bytes`.
2. **Loop over prompts.** Each user request is handled on its own. For every
   request, `build_prompt` writes one prompt: the rules, all available
   functions and this single request.
3. **Text to ids.** `llm.encode(full_prompt)` runs the tokenizer (regex split,
   BPE merges from `merges.txt`, lookup in `vocab.json`), which is ordinary code
   next to the model, not part of the neural network. The prompt becomes a list
   of about 393 ids, e.g. `" sum"` -> `2629`.
4. **One generation step.** `get_logits_from_input_ids(prompt_ids +
   generated_ids)` turns each id into its embedding vector, runs the vectors
   through the 28 transformer layers and returns one score for each of the
   151,936 tokens. The scores rank every token as the next one given the whole
   context; the highest score is the model's favourite, not a guaranteed match.
5. **Pick a legal token.** `_select_token` walks the ids from highest score
   down and takes the first one whose bytes keep the output a valid prefix of a
   function call (checked by `_checker`).
6. **Append and repeat.** The chosen id goes to `generated_ids` (fed back to the
   model at step 4) and its bytes to `generated` (read by the checker). Steps
   4-6 repeat, one token at a time, at most 256 times.
7. **Finish.** When the checker reports the JSON object complete, it is parsed
   into a `FunctionCallResult`. After the last prompt, all results are written
   to the output file.

On the first step of "What is the sum of 2 and 3?", for example, the top score
(21.23) belongs to `' {"'`, which the checker accepts, so the call starts there.

### The same idea in a real application

Production code does not write a decoder or a checker. It describes the
functions with JSON Schema, the model (through an API or a local server such as
vLLM) returns a call, and the application runs the function and sends the
result back. A simplified example in the OpenAI-style API:

```python
# 1. Plain Python functions
def fn_add_numbers(a: float, b: float) -> float:
    return a + b

FUNCTIONS = {"fn_add_numbers": fn_add_numbers}

# 2. Their description for the model: the same JSON Schema as functions_definition.json
tools = [{
    "type": "function",
    "function": {
        "name": "fn_add_numbers",
        "description": "Add two numbers together",
        "parameters": {
            "type": "object",
            "properties": {"a": {"type": "number"}, "b": {"type": "number"}},
            "required": ["a", "b"],
        },
        "strict": True,          # constrained decoding on the server (our checker)
    },
}]

messages = [{"role": "user", "content": "What is the sum of 2 and 3?"}]
response = client.chat.completions.create(model=..., messages=messages, tools=tools)
# response = ChatCompletion(
#     id="chatcmpl-...", model="...",
#     choices=[                              # one answer unless n > 1 is asked
#         Choice(
#             index=0,
#             finish_reason="tool_calls",    # stopped to call a tool, not "stop"
#             message=ChatCompletionMessage(
#                 role="assistant",
#                 content=None,              # no text, only the call
#                 tool_calls=[...],          # see `call` below
#             ),
#         ),
#     ],
#     usage=CompletionUsage(prompt_tokens=..., completion_tokens=..., total_tokens=...),
# )

# 3. The model returned a call (our FunctionCallResult)
call = response.choices[0].message.tool_calls[0]
# call = ChatCompletionMessageToolCall(
#     id="call_abc123",                      # links the result in step 5 to this call
#     type="function",
#     function=Function(
#         name="fn_add_numbers",
#         arguments='{"a": 2, "b": 3}',      # a JSON *string*, hence json.loads
#     ),
# )
args = json.loads(call.function.arguments)        # {"a": 2, "b": 3}

# 4. The application runs the function
result = FUNCTIONS[call.function.name](**args)    # 5

# 5. The result goes back to the model, which writes the final answer
messages += [response.choices[0].message,
             {"role": "tool", "tool_call_id": call.id, "content": str(result)}]
final = client.chat.completions.create(model=..., messages=messages, tools=tools)
print(final.choices[0].message.content)           # "The sum of 2 and 3 is 5."
```

| This project | Real application |
|---|---|
| `build_prompt` lists the functions | `tools=[...]`; the provider adds them to the prompt in its own format |
| `encode`, `get_logits_from_input_ids`, the generation loop | inside the API or the inference server |
| `_select_token` + `FunctionCallPrefixChecker` | `strict` mode of the API, or libraries such as XGrammar / Outlines |
| `FunctionCallResult` | `tool_calls` in the response |
| not required by the subject | running the function and sending the result back |

The subject asks only for step 3: choose the function and its arguments.

## Design decisions

- **Prefix grammar over hard-coded answers** — the model still chooses function names and argument values via logits; we only restrict the legal token set.
- **Public `llm_sdk` API only** — no private attributes; no direct Hugging Face calls in `src/`.
- **Pydantic models** for definitions, prompts, and results (`models.py`).
- **Fast constrained argmax** — scan tokens from highest logit downward and take the first legal one instead of masking the full vocabulary every time (same result, much faster when the model already prefers valid JSON).
- **Prompt built only from the loaded definitions** — each function is listed with its parameters and the exact JSON shape of a call. There are no examples taken from the test files, so nothing depends on the sample prompts. General rules (copy quoted text exactly, write a regex for what the user describes) help the 0.6B model with argument values.
- **Lenient input schema** — extra JSON-schema keys (`required`, per-parameter `description`, ...) are accepted; parameter descriptions are shown to the model.

## Performance analysis

On the bundled sample (`11` prompts):

- **Validity:** 100% parseable, schema-shaped JSON in practice.
- **Accuracy:** near-perfect function selection and argument extraction on the provided tests (sums, greetings, reverse, square root, regex substitutions).
- **Speed:** full run typically around **2–3 minutes** on an Apple Silicon Mac after the model is cached (under the 5-minute guideline). First run is slower because weights download.

Reliability comes mainly from structural masking: even when the raw model would emit prose or broken braces, those tokens are rejected.

## Challenges faced

- **Merged BPE tokens** — Qwen often emits pieces like `{"`, `":"`, `{\n`, not single characters. Constraints must validate **decoded text prefixes**, not assume one character per step.
- **Byte-level vocabulary** — `vocab.json` stores bytes, not text (`Ġ` for space, `Ã©` for `é`). Replacing only `Ġ`/`Ċ` breaks every non-ASCII character, so generation works on bytes and decodes UTF-8 incrementally.
- **Dead ends** — a checker that accepts `01` or `"\q` only fails at the closing brace, when no token can fix it. Making every partial check as strict as the final `json.loads` removed those failures.
- **Logits longer than vocab** — some ids have no vocab entry; they are skipped.
- **Regex prompts** — structure can be forced, but string *contents* still depend on the model. A generic rule (use a character class that lists every member of a kind of character) gets the sample regex prompts right without hard-coding any answer; the tiny model remains sensitive to wording.
- **Speed** — naive “test all ~150k tokens every step” was too slow; ordered logit scan fixed that.
